# Bank AI — MVP: разбивка на сервисы и дальнейшее развитие

Дополнение к базовому видению продукта. Ниже — предложение по составу
сервисов для MVP, минимально жизнеспособной архитектуре и списку того,
что можно добавить на следующих этапах.

---

## 1. Принцип формирования MVP

MVP должен закрывать один сценарий полностью, а не десять — наполовину:

> Пользователь открывает Word → выделяет текст → применяет AI-действие
> (переписать / сократить / расширить / формальнее / summary / вопрос по
> документу) → видит diff → принимает или отклоняет.

Всё, что не обслуживает этот цикл (RAG, DWH, Excel, Workspace, шаблоны),
выносится за пределы MVP, но проектируется так, чтобы не переписывать
архитектуру при добавлении.

---

## 2. Состав сервисов для MVP

### 2.1 Word Add-in (Frontend)
- Office.js task pane, работает поверх выделения (`Office.context.document.getSelectedDataAsync`)
- UI: панель действий, превью diff (track-changes стиль), кнопки Accept/Reject
- Локальный кэш последних N операций (undo-стек на стороне клиента)
- Аутентификация через SSO (см. 2.3)

### 2.2 API Gateway / BFF
- Единая точка входа для Add-in
- Маршрутизация запросов к LLM Orchestrator, Auth, Document Service
- Rate limiting на уровне пользователя/отдела
- Логирование запросов (без содержимого документа в открытом виде — см. Compliance)

### 2.3 Auth & Access Service
- Интеграция с корпоративным AD/LDAP или SSO (SAML/OIDC)
- Ролевая модель: кто какие AI-функции может использовать (для банка это критично — юрист, аналитик, операционист могут иметь разный доступ)
- Привязка к организационной единице для будущего биллинга/квот

### 2.4 LLM Orchestration Service
- Построение промпта под конкретное действие (rewrite / shorten / expand / formalize / summary / Q&A)
- Библиотека системных промптов, версионируемая отдельно от кода
- Инъекция ограничений: "сохранить цифры и факты без изменений", "не менять именованные сущности"
- Абстракция над провайдером модели (чтобы можно было переключаться между моделями/контурами — важно для банка из-за требований к размещению данных)
- Обработка ошибок модели, таймауты, ретраи

### 2.5 Document Processing Service
- Парсинг фрагмента .docx в структурированный вид (стили, списки, таблицы — чтобы не терять форматирование)
- Генерация diff между исходным и новым текстом
- Сборка результата обратно в OOXML-совместимый фрагмент для вставки в Word

### 2.6 Audit & Logging Service
- Для банка — обязателен с первого дня, не "потом"
- Кто, когда, какой документ, какое действие, какая модель
- Хранение метаданных запроса отдельно от содержимого (минимизация утечки чувствительных данных в логи)
- Возможность выгрузки для комплаенс/ИБ

### 2.7 Monitoring / Observability
- Метрики: latency LLM-вызовов, доля Accept/Reject по типам действий (это ключевой продуктовый сигнал качества)
- Алерты на рост ошибок или таймаутов провайдера модели

## 3. Схема потока данных MVP

```text
Word Add-in
   │  (выделенный текст + действие)
   ▼
API Gateway ── Auth Service (проверка токена/роли)
   │
   ▼
LLM Orchestration Service ── Prompt Library
   │
   ▼
LLM Provider (внутренний контур / корпоративная модель)
   │
   ▼
Document Processing Service (сборка диффа, форматирование)
   │
   ▼
Word Add-in (показ diff, Accept/Reject)
   │
   ▼
Audit Service (лог действия)
```

## 4. Что сознательно НЕ входит в MVP

| Функция | Почему не в MVP | Когда добавить |
|---|---|---|
| RAG по внутренним документам | Требует пайплайна индексации, векторной БД, прав доступа на уровне документа | Фаза 2 |
| Интеграция с DWH | Нужна отдельная безопасная шина данных, согласование с владельцами данных | Фаза 3 |
| Excel Add-in | Другой UI-слой, другая модель данных (таблицы/формулы) | Фаза 2–3 |
| Fact-checking / автоцитирование | Зависит от готового RAG и источников | После RAG |
| Корпоративные шаблоны | Организационный вопрос (кто владелец шаблонов), не чисто техническая задача | Фаза 2 |
| Bank AI Workspace (единый портал) | Имеет смысл только когда есть 2+ канала использования (Word + Excel + Web) | Фаза 3–4 |

---

## 5. Roadmap по фазам

**Фаза 0 — MVP (описано выше)**
Rewrite / Shorten / Expand / Formalize / Summary / Q&A по выделенному фрагменту, diff-превью, аудит, роли доступа.

**Фаза 1 — Укрепление MVP**
- Q&A по всему открытому документу (не только по выделению)
- Библиотека избранных промптов/действий для пользователя
- Метрика качества: доля принятых правок, A/B системных промптов

**Фаза 2 — Знания**
- RAG по внутренним документам (векторный поиск + права доступа, синхронизированные с корпоративными ACL)
- Корпоративные шаблоны документов с автозаполнением через AI
- Excel Add-in (первая версия: объяснение формул, генерация формул, краткие сводки по диапазону)

**Фаза 3 — Данные и доверие**
- Подключение DWH для автоматической подстановки актуальных показателей в отчёты
- Fact-checking сгенерированного текста против внутренних источников
- Автоматическое цитирование источника рядом с фрагментом текста
- Автообновление регулярных отчётов за новый период (сравнение с предыдущей версией + подстановка новых цифр)

**Фаза 4 — Платформа**
- Единый Bank AI Workspace: история всех действий пользователя по всем каналам (Word/Excel/Web)
- Централизованное управление промптами и моделями для админов
- Квоты и биллинг по подразделениям

## 6. Специфика для банка — что важно не забыть

- **Данные не должны покидать периметр** без явного разрешения — модель должна быть либо развёрнута внутри контура, либо проходить через шлюз с маскированием PII/чувствительных сумм и реквизитов.
- **Иммутабельный аудит-лог** — требование ИБ и регулятора, не опция.
- **Разграничение доступа на уровне документа**, а не только на уровне функции — иначе RAG в фазе 2 станет утечкой данных между подразделениями.
- **Human-in-the-loop обязателен** — ни одно изменение не применяется без явного Accept пользователя (уже заложено в MVP через diff-превью, важно не убирать этот шаг даже ради UX-упрощения).
- **Версионирование промптов отдельно от релизов кода** — комплаенс может потребовать отдельного согласования формулировок системных промптов.

---

## 7. Дополнительные идеи на будущее

- Режим "стиль подразделения" — модель дообучается/настраивается под тон конкретного департамента (юридический, PR, риск-менеджмент)
- Плагин для проверки документа на соответствие внутренним нормативным актам (не просто грамматика, а комплаенс-чек)
- Совместная работа: AI-комментарии как обычные комментарии Word, видимые другим соавторам
- Экспорт истории AI-правок как отдельного лога изменений для аудита конкретного документа
- Локальный "sandbox"-режим для черновиков без сохранения в аудит (для действительно черновых набросков), с явной маркировкой в UI, что это исключение из общего правила аудита

## 8. Вариант поставки MVP: локальный установщик для Windows

Для первого пилота расширение можно распространять не через публичный Microsoft
Marketplace и не через общий сервер, а в виде локального Windows-установщика:

```text
BankAI-Setup.exe
```

Каждый участник пилота устанавливает Bank AI на свой компьютер. После установки
расширение работает непосредственно внутри настольного Microsoft Word, а не как
отдельный сайт или текстовый редактор.

### 8.1. Пользовательский сценарий

1. Пользователь запускает `BankAI-Setup.exe` один раз.
2. Установщик размещает локальное приложение и регистрирует Word Add-in.
3. Пользователь открывает Microsoft Word.
4. На ленте или в списке дополнений появляется Bank AI.
5. Пользователь выделяет текст и открывает боковую панель.
6. Выбирает Rewrite, Shorten, Expand или Formalize.
7. Видит исходный и предложенный варианты.
8. Нажимает Accept для замены выделения либо Reject для отмены.

Пользователь продолжает работать с обычным `.docx`-документом. Чтение выделения
и применение результата выполняются через Office.js внутри Word.

### 8.2. Локальная архитектура

```text
Microsoft Word
   │ Office.js: чтение и замена выделенного текста
   ▼
Bank AI Task Pane
   │ HTTPS-запрос на localhost
   ▼
Локальное приложение Bank AI
   ├── API для панели Word
   ├── библиотека промптов
   ├── валидация запросов и ответов
   ├── локальный журнал операций
   └── клиент AI-провайдера
          │
          ▼
AI API / корпоративный AI Gateway / локальная модель
```

Локальное приложение запускает HTTPS-сервер только на loopback-интерфейсе,
например `https://127.0.0.1:3847`. Сервер не должен слушать `0.0.0.0`:
подключаться к нему должен только Word на том же компьютере.

В `manifest.xml` адрес панели указывает на локальное приложение:

```xml
<SourceLocation DefaultValue="https://localhost:3847/taskpane.html" />
```

Если приложение не запущено, Word не сможет открыть панель. Поэтому установщик
настраивает его автоматический запуск при входе в Windows. В MVP приложение
можно показывать в системном трее со статусом `Bank AI: работает` и командами
Restart, Diagnostics и Exit.

### 8.3. Что делает установщик

- копирует приложение в профиль текущего пользователя;
- устанавливает или обновляет локальный HTTPS-сертификат;
- настраивает автозапуск приложения;
- регистрирует manifest дополнения для Word;
- создаёт диагностику и деинсталлятор;
- при обновлении сохраняет настройки пользователя и локальный журнал;
- при удалении убирает manifest, автозапуск и созданный сертификат.

Для MVP предпочтительна установка в профиль пользователя, а не в `Program
Files`. Это уменьшает вероятность запроса административных прав.

### 8.4. Права администратора и корпоративные ограничения

Само приложение можно установить без прав администратора, если все файлы и
настройки записываются только в профиль текущего пользователя. Однако
гарантировать установку без участия IT на корпоративном компьютере нельзя.

| Операция | Ожидаемые права |
|---|---|
| Копирование приложения в профиль пользователя | Обычно без администратора |
| Автозапуск для текущего пользователя | Обычно без администратора |
| Настройки Office в `HKEY_CURRENT_USER` | Обычно без администратора |
| Доверие локальному HTTPS-сертификату | Может потребовать администратора или разрешения IT |
| Установка для всех пользователей | Требует администратора |
| Установка Windows Service | Требует администратора |
| Изменение firewall и политик Office | Требует администратора или IT |

В корпоративной среде запуск неизвестных `.exe`, установка сертификатов,
sideloading Office Add-ins и изменение автозапуска могут быть запрещены
групповыми политиками, Microsoft Defender или средствами управления устройствами.
Перед пилотом нужно согласовать с IT/ИБ:

- возможность запуска подписанного установщика;
- способ доверия локальному сертификату;
- разрешение на установку внутреннего Word Add-in;
- список тестовых пользователей и устройств;
- допустимый AI-провайдер и правила передачи текста.

Для тестирования manifest можно загружать вручную или через доверенный сетевой
каталог Office. Такой способ предназначен для разработки и пилота, но не для
промышленной эксплуатации. Если ручная установка запрещена, администратор
Microsoft 365 централизованно назначает manifest тестовой группе через
Integrated Apps. Локальное приложение при этом всё равно устанавливается на
каждый компьютер.

### 8.5. Модель безопасности

Локальный сервер должен принимать запросы только с ожидаемого origin панели Word
и только на loopback-интерфейсе. Минимальная защита включает:

- HTTPS между Word WebView и локальным приложением;
- случайный локальный токен, создаваемый при установке;
- проверку допустимых действий вместо приёма произвольных промптов;
- ограничение размера передаваемого текста;
- отсутствие исходного текста в технических логах по умолчанию;
- явное подтверждение пользователя перед изменением документа;
- подпись установщика сертификатом издателя перед широким пилотом.

Общий ключ внешнего AI API нельзя считать защищённым, если он находится внутри
локального приложения: пользователь с доступом к компьютеру потенциально может
его извлечь. Возможны три модели подключения:

1. Пользователь вводит собственный API-ключ — только для технического прототипа.
2. Приложение получает краткоживущий токен и обращается к корпоративному AI Gateway — предпочтительно для банка.
3. Приложение обращается к одобренной локальной модели на рабочем компьютере.

Для банковского пилота рекомендуется корпоративный AI Gateway с аутентификацией,
квотами и централизованным аудитом. Внешний AI API допустим только на
обезличенных тестовых данных и после согласования с ИБ.

### 8.6. Обновление приложения

У локальной поставки две независимо обновляемые части:

- локальное приложение: UI, API, промпты и интеграция с моделью;
- manifest Word Add-in: название, разрешения, адрес панели и кнопки на ленте.

Изменения интерфейса и промптов доставляются обновлением локального приложения.
Если меняются кнопки Word, разрешения или структура manifest, дополнение может
потребоваться зарегистрировать заново. Для раннего MVP достаточно выпускать
новый подписанный установщик вручную. Автообновление следует добавить после
успешного пилота.

### 8.7. Ограничения подхода

- Первая версия ориентирована только на настольный Word для Windows.
- При выключенном локальном приложении панель Word не работает.
- Установка и обновление выполняются отдельно на каждом компьютере.
- Общий секрет AI нельзя безопасно поставлять внутри `.exe`.
- Корпоративные политики могут потребовать централизованной установки через IT.
- Локальные аудит-логи сложнее централизованно собирать и защищать.
- Вариант удобен для небольшого пилота, но хуже масштабируется на сотни пользователей.

### 8.8. Рекомендуемый объём первой версии

- поддержка настольного Word для Windows;
- получение текущего текстового выделения;
- действия Rewrite, Shorten, Formalize, Grammar, Translate, Expand и Change Tone;
- предпросмотр «Было / Стало»;
- Accept и Reject;
- локальное приложение в системном трее;
- экран настройки подключения к AI;
- диагностика Word Add-in, сертификата и AI;
- простой локальный аудит без сохранения содержимого документа.

SSO, роли, централизованные обновления, Q&A по всему документу, сложный OOXML-
diff и корпоративный сбор логов добавляются после того, как пилот подтвердит
ценность основного сценария.

### 8.9. Переход к промышленной версии

Локальный MVP не является тупиковой архитектурой. После пилота можно сохранить
тот же интерфейс Word и заменить только способ подключения:

```text
Пилот:                Word → localhost → AI
Промышленная версия:  Word → корпоративный API Gateway → AI
```

После перехода локальный сервер и отдельный установщик больше не обязательны:
manifest централизованно разворачивается через Microsoft 365, а панель и backend
размещаются во внутреннем контуре. Пользовательский сценарий внутри Word при
этом не меняется.

## 9. Будущее развитие: стили и оформление документов

В продукте нужно разделять два вида стилей:

1. **Стиль текста** — официальный, юридический, краткий или деловой тон. Эта
   функция меняет содержание и формулировки с помощью AI.
2. **Стиль документа Word** — заголовки, шрифты, интервалы, списки, цвета,
   таблицы и общая структура. Эта функция меняет оформление документа.

Текстовый стиль частично входит в MVP через действие Formalize. Полноценное
управление оформлением добавляется после проверки основного сценария MVP.

### 9.1. Пользовательский сценарий

Пользователь сможет применить оформление:

- к выделенному фрагменту;
- к текущему разделу;
- ко всему документу;
- через готовый корпоративный шаблон.

Пример выбора в панели Word:

```text
Стиль документа

○ Официальное письмо
○ Служебная записка
○ Кредитное заключение
○ Аналитический отчёт
○ Корпоративный стандарт банка
```

После выбора Bank AI анализирует документ и формирует план изменений:

```text
Найдено:
- 7 заголовков с неправильным стилем;
- 3 разных шрифта в основном тексте;
- 4 списка с нарушенной нумерацией.

[Применить выбранные] [Применить все] [Отмена]
```

Изменения оформления, как и изменения текста, не должны применяться без явного
подтверждения пользователя.

### 9.2. Какие элементы можно оформлять

- название документа;
- заголовки и подзаголовки разных уровней;
- основной текст;
- абзацные отступы и интервалы;
- шрифт, размер и начертание;
- выравнивание;
- маркированные и нумерованные списки;
- нумерацию разделов;
- таблицы и подписи к ним;
- цитаты и примечания;
- реквизиты и блок подписи;
- колонтитулы и номера страниц.

### 9.3. Именованные стили Word

Предпочтительно применять не набор независимых параметров к каждому фрагменту,
а именованные стили Word:

```text
BankTitle
BankHeading1
BankHeading2
BankBody
BankTable
BankQuote
BankSignature
```

Это позволяет сохранять единообразие документа и централизованно менять дизайн.
Например, изменение шрифта в `BankHeading1` обновит все заголовки первого уровня,
к которым применён этот стиль.

Корпоративный профиль оформления можно описывать отдельно от кода:

```json
{
  "id": "service-memo-v1",
  "name": "Служебная записка",
  "version": 1,
  "styles": {
    "title": "BankTitle",
    "heading1": "BankHeading1",
    "heading2": "BankHeading2",
    "body": "BankBody",
    "table": "BankTable",
    "signature": "BankSignature"
  },
  "defaults": {
    "font": "Arial",
    "fontSizePt": 11,
    "lineSpacing": 1.15
  }
}
```

Профили должны иметь версию, владельца и дату утверждения, чтобы изменение
корпоративного стандарта можно было согласовать и отследить.

### 9.4. Что необходимо заложить уже в MVP

Хотя полноценное применение стилей не входит в первую версию, MVP не должен
мешать развитию этой функции. Поэтому первая реализация обязана:

- по возможности сохранять оформление заменяемого выделения;
- не преобразовывать весь результат в неформатированный обычный текст;
- отделять текстовое содержимое от метаданных оформления;
- определять текущий именованный стиль Word;
- применять AI-изменение только к выбранному диапазону;
- не менять оформление за пределами выбранного диапазона;
- корректно сообщать пользователю, если сложное форматирование сохранить нельзя;
- тестировать обычные абзацы, заголовки и простые списки отдельно.

Таблицы, сноски, колонтитулы, вложенные списки и сложный OOXML не считаются
полностью поддерживаемыми в MVP. Для них расширение должно либо сохранить
исходное оформление, либо отказаться от автоматической замены и показать
понятное предупреждение.

### 9.5. Этапы реализации

**Этап 1 — сохранение форматирования в MVP**

- заменить текст без намеренного изменения его текущего оформления;
- сохранить стиль абзаца и основные свойства выделения;
- поддержать обычный текст, заголовки и простые абзацы.

**Этап 2 — простые действия форматирования**

- «Оформить как заголовок»;
- «Оформить как основной текст»;
- «Привести списки к единому виду»;
- «Очистить случайное форматирование»;
- «Применить стандартный шрифт и интервалы».

**Этап 3 — корпоративные профили**

- готовые стили для разных видов банковских документов;
- проверка документа на соответствие выбранному профилю;
- предпросмотр найденных нарушений;
- выборочное или полное применение исправлений;
- версионирование и централизованное обновление профилей.

**Этап 4 — шаблоны документов**

- создание документа по утверждённому шаблону;
- обязательные секции и реквизиты;
- проверка структуры и заполненности;
- AI-помощь при заполнении разделов;
- экспорт отчёта о соответствии корпоративному стандарту.

### 9.6. Безопасное применение изменений

AI может помогать классифицировать элементы документа — например, определять,
что конкретная строка является заголовком или подписью. Однако итоговое
форматирование должно выполняться детерминированными правилами выбранного
профиля, а не свободно генерироваться моделью.

```text
Документ
   ▼
Анализ структуры
   ▼
Список предполагаемых элементов и нарушений
   ▼
Предпросмотр изменений
   ▼
Подтверждение пользователя
   ▼
Применение именованных стилей Word
```

Такой подход делает результат повторяемым, снижает риск повреждения документа и
позволяет объяснить, какое правило вызвало каждое изменение.

## 10. Реализованный каркас первого MVP

В репозитории создан минимальный запускаемый каркас:

```text
packages/
├── addin/          # панель внутри Word и Office.js
├── contracts/      # общие типы запросов и ответов
└── local-runtime/  # локальный HTTPS API и AI Provider
```

Подробные технические решения описаны в [`docs/ARCHITECTURE.md`](docs/ARCHITECTURE.md).

### 10.1. Запуск в режиме разработки

Требуются Node.js 20 или новее и установленный Microsoft Word.

```bash
npm install
npm run typecheck
npm test
npm run build
npm start
```

При первом запуске Office Add-in требуется доверенный локальный HTTPS-сертификат.
Его можно установить отдельной командой:

```bash
npx office-addin-dev-certs install
```

Операционная система может запросить пароль администратора или подтверждение
добавления локального центра сертификации. После успешной установки runtime
будет доступен по адресу `https://localhost:3847`, а проверка состояния — по
адресу `https://localhost:3847/health`.

Затем `packages/addin/manifest.xml` нужно загрузить в Word как тестовое
дополнение. Способ sideloading зависит от платформы и корпоративных политик
Office. Для пилота на Windows manifest можно назначить через доверенный сетевой
каталог либо централизованно через Microsoft 365 Integrated Apps.

### 10.2. Текущее состояние

- реализованы Rewrite, Shorten, Formalize и проверка грамматики;
- реализован перевод между русским, казахским и английским с сохранением числовых реквизитов;
- реализованы расширение текста и изменение тона (нейтральный, вежливый, строгий, дипломатичный);
- реализовано краткое содержание выделенного фрагмента с сохранением ключевых фактов и реквизитов;
- реализовано чтение текущего выделения через Office.js;
- реализован предпросмотр «Было / Стало»;
- изменённые слова подсвечиваются в блоке «Стало»;
- реализованы Accept и Reject;
- локальный API валидирует действие и ограничивает текст 20 000 символами;
- runtime слушает только `127.0.0.1`;
- подключены mock-провайдер и OpenAI-совместимый LiteLLM Chat Completions API;
- добавлены typecheck, сборка и минимальный тест провайдера.

Подробный актуальный чек-лист находится в [PROGRESS.md](PROGRESS.md).

Для реальной генерации создайте локальный `.env` на основе `.env.example`:

```dotenv
BANK_AI_PROVIDER=litellm
LLM_API_KEY=
LLM_API_BASE=https://prod-litellm.nationalbank.kz
LLM_MODEL=Qwen/Qwen3.5-35B-A3B-FP8
```

`LLM_API_KEY` заполняется пользователем самостоятельно и не должен попадать в
Git или в код Word Add-in. Mock-провайдер остаётся доступен через
`BANK_AI_PROVIDER=mock` для проверки интерфейса без API-ключа и внешних запросов.
